# Security analysis

This analysis is written from the measured outputs in `docs/results.md`. No
number below is estimated or copied from a paper; the single source of truth is
the evaluation script. The dataset snapshot is described in `docs/data_audit.md`.

## What the prototype does

DomainGuard scores **strings only**. It parses a URL or domain with a bundled
public-suffix list, extracts fixed numeric features, and applies one of three
random forests. It never resolves, fetches, or contacts a scored name. A unit
test patches sockets and HTTP libraries and confirms the check and scan paths
work with all network access blocked.

The DNS scanner applies two detectors to each unique registered domain and
ranks a client only after at least three flagged domains (the default
`--min-flags`). NXDOMAIN rate is displayed but is never a feature, never part of
ranking, and never part of an accuracy number.

## What does not work

- **Phishing F1 target missed.** At the 1% false-positive operating point the
  phishing model's recall is far below the 0.95 F1 goal. The precise measured
  values are in `docs/results.md`. High precision is bought at the cost of
  missing many malicious URLs; lowering the threshold would raise recall but
  break the fixed FPR requirement.
- **Path features add little.** `phish_full` is reported as a comparison only.
  The path group is a confound: malicious URLs in the source feed often carry
  query strings or paths that benign Tranco URLs do not, so a gain from path
  features would not prove better host-level generalisation. The ablation table
  in `docs/results.md` reports the measured effect.
- **External DGA gap.** Recall on the held-out ExtraHop sample is much lower
  than on our generated test families. The generated families are shape
  templates, not real malware output, so strong in-domain results must not be
  read as real-world accuracy. FPR on external benign names is also measured
  and reported, not assumed.
- **Dictionary-style DGAs and simple rewrites.** Some evasion families are
  almost entirely missed. A few string edits leave detection unchanged and a
  few change it sharply; both directions are reported. The scanner's
  domain-level recall on simulated traffic is low because DNS logs expose only
  the registered domain, while `phish_host` was trained on full URL strings.
- **Simulated traffic is not real traffic.** The DNS log is generated from the
  held-out test partition with a fixed set of client archetypes. Client-level
  precision/recall on that log says nothing about real networks, encrypted DNS,
  resolver behaviour, or genuine infection prevalence.
- **No attribution.** Feature contributions shown by `check` are value × global
  forest importance. They are approximate global explanations, not per-prediction
  causal reasons.

## Misuse and safety considerations

- The only artefacts emitted are scores, thresholds and domain-name strings.
  The DGA generators produce names, not executables or network tooling, and
  evasion transforms are plain string edits.
- A false positive can wrongly implicate a domain or a client. The minimum
  evidence rule reduces one-off false alarms but does not remove them; a human
  must review any flag before action.
- OpenPhish's feed was downloaded under academic-research terms and is never
  committed or redistributed. Raw Tranco, phishing lists and ExtraHop data are
  gitignored. No downloaded dataset, trained model or raw DNS log is in git.
- The Flask demo binds to `127.0.0.1` by default, has debug off, autoescaping
  on, CSRF tokens, a 20 MB upload cap, and deletes temporary uploads before the
  response. It is a local demo, not an internet-facing service.

## Lessons learned

1. Fixed 1%/0.1% FPR thresholds make precision look excellent even when recall
   is weak; both numbers must always be shown together.
2. Grouped splits and a held-out real dataset expose gaps that random splits
   and synthetic test families hide.
3. Caching repeated feature work and compressing model artefacts changed only
   runtime and disk use, not any measured value.
4. A scanner that sees only DNS names cannot inherit the performance of a URL
   classifier that saw paths and query strings.
